이 문서는 md 가 원본이다 (2026-08-27 이관). 전에는 HTML 을 손으로 고쳤고, 그래서 결정이 바뀌어도 이 페이지만 낡은 채 남았다. 폐기된 저장소 이름과 옛 갈래 어휘가 여기 살아 있었다. 이제 md 를 고치면 웹이 따라온다.

1. 손으로 하는 것은 하나뿐이다

순서무엇을 한다보드누가
1이슈를 만든다. 본인에게 배정하고 기간을 넣는다Todo자동
2폼에서 「작업 영역」과 「어느 관문까지」를 고른다라벨 · 마일스톤자동
3작업 전 브랜치를 판다본인
4이슈를 In Progress 로 옮긴다In Progress본인 (손으로)
5작업하고 커밋한다본인
6PR 을 연다. 본문에 Closes #번호In Progress자동
7팀장이 확인한다팀장
8머지되면 이슈가 자동으로 닫힌다Done자동

4번 하나만 손으로 합니다. 나머지는 전부 자동입니다.

Closes #29 는 PR 을 열 때가 아니라 머지될 때 이슈를 닫습니다. 그래서 PR 이 먼저입니다. main 에 안 들어간 작업은 아직 끝난 것이 아닙니다.

2. 이슈를 만들면 무엇이 일어나나

언제무엇이어디서
이슈 생성보드에 Todo 카드가 생긴다GitHub Projects
이슈 생성시작·종료 날짜가 박힌다issue-dates.yml
이슈 생성담당자가 작성자로 지정된다GitHub Projects
이슈 생성·수정폼의 답이 라벨·마일스톤이 된다issue-triage.yml
이슈 생성·수정팀장 텔레그램으로 알림issue-triage.yml
이슈 닫힘보드가 Done 으로GitHub Projects

폼의 답이 옮겨지는 것이 핵심입니다. 전에는 「어느 갈래인가」를 물어놓고 그 답이 본문 글자로만 남아 보드에서 묶이지 않았습니다. 팀원이 안 적어서가 아니라 적은 것이 옮겨지지 않아서 팀장이 손으로 분류하고 있었습니다.

작업 영역을 안 고르면 팀장 텔레그램에 「분류 안 됨」 이 갑니다. 조용히 넘어가지 않습니다.

이슈 템플릿

템플릿언제어디
작업 등록이런 작업을 하겠다고 미리 올릴 때lab · go2
실험 기록가설 하나, 변경 하나. 결과를 숫자로 판정할 때go2
리서치답을 모르는 질문이 있을 때lab
막힘·오류안 되는 것이 있을 때lab · go2

빈 이슈로 만들지 않습니다. 목록에서 골라야 폼이 뜨고, 폼이 있어야 자동 분류가 됩니다.

3. 문서를 올리면 무엇이 일어나나

출력
inbox/<내이름>/ 에 md 를 올리고 PR
        ↓
① 디스코드 알림                          팀에 새 제출을 알린다
② 팀장 텔레그램 검수 결과                 무엇이 갖춰졌고 무엇이 빠졌나
③ PR 코멘트: 채워진 머리 다섯 줄          복사해서 붙이면 끝
        ↓
팀장이 확인하고 머지
        ↓
④ [승격 검토] 이슈 생성                   남은 일(정본으로 옮기기)만 추적
        ↓
팀장이 docs/ 로 승격
        ↓
⑤ 다음 웹 빌드에 페이지로 나간다

③이 새로 생긴 것입니다. 문서 머리 다섯 줄이 없으면 봇이 채워진 블록을 코멘트로 달아 줍니다. 무엇을 어떻게 쓰라고 설명하는 것보다 완성된 예시를 주는 게 빠릅니다.

봇이 채우는 것과 못 채우는 것이 갈립니다.

줄봇이 채우나
> 작성: 이름 · 날짜 시각채운다 (PR 작성자를 이름으로 바꿔서)
> 상태: 초안채운다
> 분류: > 근거: > 요지:못 채운다. 내용을 읽어야 안다

4. 그 밖에 저절로 도는 것

언제무엇워크플로
PR 이 열리면디스코드 알림pr-notify.yml
PR 이 머지되면디스코드 알림merge-notify.yml
이슈가 닫히면완료 날짜 기록done-date.yml
월요일 09시주간 리포트 + WBS 엑셀 생성weekly-report.yml
일요일 21시다이제스트 재료 수집weekly-digest.yml
조선대 자료가 올라오면감지 알림lecture-watch.yml
마감이 다가오면알림deadline-alert.yml
main 에 직접 push 하면감지하고 안내main-guard.yml

다이제스트는 왜 「재료」만 모으나

다이제스트는 「무엇을 알게 됐나」 를 쓰는 문서입니다. 그건 판단이라 기계가 대신 못 씁니다. 커밋 목록에서 「보상이 높다고 걷는 것이 아니다」 같은 문장은 나오지 않습니다. 기계가 흉내 내면 그럴듯하고 틀린 글이 남습니다.

그래서 모으는 일만 자동으로 합니다. PR · 닫힌 이슈 · 새 문서 · 커밋을 모아 팀장 텔레그램으로 보냅니다. 쓰는 일은 사람이 합니다.

5. 아직 자동이 아닌 것

무엇왜 사람이 하나
Todo → In Progress「지금 시작했다」는 본인만 안다
inbox → docs/ 승격무엇을 정본으로 올릴지는 판단이다
다이제스트 본문위 참조
산출물 상태를 확정 으로완료 기준을 보고 사람이 판정한다
마일스톤 지정「언제까지 끝나야 하나」는 담당자만 안다

6. 브랜치와 커밋

출력
feature/주제-이름      새로 만드는 것
fix/무엇이안되나-이름    고치는 것
docs/문서명-이름        문서만

이슈 번호를 붙이지 않습니다. 뒤에 자기 이름을 붙입니다. 다섯이 같은 주제를 만져도 브랜치가 안 겹칩니다.

이름임석헌맹라현오현민오흥재이민우
브랜치 약자limmeangohjaylee
GitHub 핸들IQ152maengu86less82vfxpedialmw0207

추적의 핵심은 브랜치 이름이 아니라 커밋·PR 의 Closes #번호 입니다. 이것만은 반드시.

foothold-go2 는 한 단계가 더 있습니다. 코드 저장소라 검증된 것만 main 에 둡니다.

출력
feature/…  ->  PR  ->  dev  ->  검증된 것만 PR  ->  main

머지된 브랜치는 지웁니다. 브랜치는 소모품입니다.

7. 어디에 무엇을 올리나

무엇어디에어떻게
문서 (정리 안 된 것 포함)inbox/<내이름>/PR. 팀장이 확인하고 머지
코드sim/ nav/ common/브랜치 → PR. inbox 를 거치지 않는다
정본 문서 docs/직접 고치지 않는다팀장이 inbox 에서 승격

코드가 inbox 를 안 거치는 이유: 문서는 팀장이 옮겨도 뜻이 안 변하지만 코드는 옮기면 도는지 보장할 수 없습니다.

폴더가 작업 영역과 짝을 이룹니다

작업 영역폴더주담당

이슈에 A/평가 가 붙으면 코드는 sim/eval/ 입니다. 찾을 때 헤매지 않습니다.

8. AI 를 쓸 때

AI 가 썼어도 올리는 사람은 본인이다

AI 가 만든 글이든 코드든 PR 을 올린 사람이 책임집니다. 읽지 않고 올리지 않습니다.

지어낸 것을 거른다

AI 는 없는 함수·없는 논문·없는 수치를 자신 있게 만들어 냅니다. 숫자와 출처는 반드시 눈으로 확인하십시오.

직접 본 것과 들은 것을 구분한다

주장에 신뢰도를 답니다. 이게 이 팀 문서의 핵심 규칙입니다.

출력
`확인됨`   직접 보거나 재서 확인한 것
`추측`     그럴듯하지만 확인 안 한 것
`미확인`   확인이 필요한 것
`미측정`   재보지 않은 수치

재보지 않은 것에 「확인했다」를 쓰지 마십시오. 확인 비용이 2분이면 확인하십시오.

비공개 자료를 통째로 넣지 않는다

조선대 강의 자료 원본 · 팀 내부 문서 · 계정 정보 · 개인정보는 AI 에 넣지 않습니다.

코드는 돌려보고 올린다

AI 가 준 코드가 도는지 확인하고 올립니다. 「그럴듯한 코드」와 「도는 코드」는 다릅니다.

AI 사용을 숨길 필요는 없다

우리는 AI 를 씁니다. 문제는 쓰는 것이 아니라 확인 없이 올리는 것입니다.

9. AI 에이전트에게 시킬 때 걸리는 것

작업 전에 반드시 git pull origin main

옛 상태에서 갈라진 브랜치로 작업하면 AI 는 그 시점의 저장소만 봅니다. 오래된 상태를 주면 오래된 답이 나옵니다. 8/25 와 8/26 에 같은 사고가 두 번 났습니다.

저장소 루트의 AGENTS.md 를 읽게 하십시오

Cursor 와 Codex 는 자동으로 읽습니다. Claude Code 는 CLAUDE.md 를 읽는데 그것도 같은 곳을 가리킵니다. 여러분이 따로 하실 일은 없습니다.

개인 작업 방식은 AGENTS.md 에 적지 말고 inbox/<이름>/AGENTS.md 를 만들거나 로컬 설정(gitignore 대상)으로 두십시오. 공통 파일에 개인 설정이 섞이면 다른 사람의 에이전트가 그것을 규칙으로 읽습니다.

AI 가 거의 확실하게 걸리는 것

무엇왜
em dash (긴 줄표)AI 가 습관처럼 씁니다. 빌드가 배포를 멈춥니다
선으로 그린 글자 도식표로 바꿔야 합니다
근거 표기 없는 단정확인됨/추측/미확인 을 답니다
머리 다섯 줄 누락PR 봇이 채워진 블록을 줍니다

「폐기된 사실」 관문이 2026-08-27 에 생겼습니다. 사실은 문서에만 있는 것이 아니라 빌드 스크립트에도 박혀 있고, 거기 박힌 것은 문서를 고쳐도 안 바뀝니다. 실제로 문서를 다 고쳤는데 웹에 옛 저장소 이름이 살아남은 일이 있었습니다.

11. 실수로 main 에 push 했다면

팀원이 할 것 (세 가지뿐)

  1. 더 만지지 마십시오. 되돌리려다 더 꼬입니다
  2. 팀장에게 알리십시오. 무엇을 push 했는지만
  3. 기다리십시오

팀장이 할 것

되돌릴지 그대로 둘지 판단하고 처리합니다. main-guard.yml 이 감지해서 알려 줍니다.

12. 신경 쓰지 않아도 되는 것

무엇왜
웹 배포팀장이 빌드합니다. foothold-site 를 직접 고치지 마십시오 (미러입니다)
라벨·마일스톤 붙이기폼에서 고르면 자동입니다
보드 카드 만들기이슈를 만들면 자동입니다
문서 형식 완벽하게 맞추기inbox/ 는 자유입니다. 봇이 알려 줍니다

13. 기억할 것은 이것뿐입니다

출력
1. 작업 전에 git pull origin main
2. 이슈를 만들고 「작업 영역」을 고른다
3. 시작하면 In Progress 로 옮긴다
4. 커밋·PR 에 Closes #번호

나머지는 자동입니다. 막히면 「막힘·오류」 이슈로 올려 주십시오.
